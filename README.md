# PROBIV.CC — демонстрационный форум (аудированная сборка)

Статический frontend-макет форума на HTML/CSS/JS **без сборщика и зависимостей**. Все пользователи, сообщения, рейтинги,
«депозиты» и т. п. — **синтетические**. Данные хранятся в браузере (`localStorage`). Это демо, а не production:
см. «Ограничения».

## Демо-доступ
| Роль | Данные |
|---|---|
| Администратор | логин `admin`, пароль `DEMO-ADMIN-2026` (вход через `login.html`) |
| Приглашение | код `DEMO-2026` |
| Обычный участник | любое имя из демо-базы (например `Alex22`) + любой непустой пароль; аккаунты, созданные через регистрацию, проверяют пароль |

Админ-сессия без собственной учётной записи форума работает как демо-пользователь #1 (`reagent`).
Вход по приглашению даёт **чтение** закрытых тем, но не личность пользователя (писать, реагировать и создавать темы нельзя).

## Запуск
Локально — любой статический сервер (рекомендуется, чтобы `localStorage` вёл себя как на хостинге):
```
python3 -m http.server 8000      # затем http://localhost:8000/
```
Открытие `index.html` напрямую (`file://`) тоже работает (проверено в Chromium).

## Публикация на GitHub Pages
1. Создайте репозиторий, залейте содержимое папки в ветку `main`.
2. Settings → Pages → Source: **GitHub Actions**. Workflow `.github/workflows/pages.yml` сначала запускает статические проверки,
   затем публикует только нужные файлы.
3. Все пути относительные — сайт работает и из корня домена, и из подпути (`https://user.github.io/repo/`). Проверено.
4. Свой домен: Settings → Pages → Custom domain (+ DNS CNAME), файл `CNAME` добавлять не нужно при деплое через Actions.

## Админка — где что менять
Главная → «Карта сайта» показывает каждый блок отдельно. Основные редакторы: Шапка; Верхние баннеры; Статистика; Горячие темы;
Списки тем; Разделы на главной; Правая колонка; Нижние баннеры; Форум → Разделы/Темы/Сообщения; Медиа → Медиатека и
Рекламные блоки (визуальный конструктор: перетаскивание/размер в живом предпросмотре); Пользователи; Приглашения;
Навигация; Страницы (Правила/Помощь); Резервная копия (экспорт/импорт/сброс).

Медиа-слоты: `topAd`, `hero1`, `hero2`, `sidebar`, `globalTop`, `globalBottom` (все страницы), `bottom1..4`, `threadBefore/After`.
Файл ≤ 1,5 МБ (общий лимит `localStorage` ≈ 5 МБ; при нехватке места админка сообщает об ошибке и **не** делает вид, что сохранила).

## Резервное копирование и восстановление
* **Копия:** Админка → «Инструменты/Резервная копия» → «Скачать JSON». Файл не содержит учётные данные админа.
* **Восстановление:** там же → «Импортировать» → выбрать файл → подтвердить. Данные заменяются **точно** содержимым файла
  (удалённые записи не возвращаются из начальной базы). Файл проходит проверку структуры; битый JSON отклоняется без изменений.
* **Сброс:** «Сбросить» возвращает исходную синтетическую базу (с подтверждением).

## Ограничения (важно)
* `localStorage`, демонстрационные логины и «проверка пароля» в JavaScript — **не защита**: клиентский код и данные доступны
  посетителю, админ-сессию можно подделать в консоли. Для production нужны серверная авторизация и RLS (`docs/SUPABASE_MIGRATION.md`).
* Числовые «демо-счётчики» (статистика, число тем/сообщений раздела, «ответы» темы) — отображаемые значения, а не вычисляемые.
* Данные хранятся отдельно в каждом браузере; нет синхронизации между вкладками/устройствами.
* Удаление пользователя в админке (поведение сохранено) переназначает его темы/сообщения первому другому пользователю.


## Supabase bridge (v10)
See `docs/SUPABASE_MIGRATION.md` and apply `supabase/001_schema.sql` manually in Supabase SQL Editor. The frontend uses `supabase-config.js` (public key only) and `supabase-adapter.js`. This compatibility bridge is not a complete production migration of every legacy forum action; the SQL has not been applied to the live project from this environment.
